# AGENTS.md

Onboarding for coding agents working on faro. Read this first, then the docs it points to.

## What faro is

A terminal (TUI) client for Signal, written in Rust, built for people who run everything over SSH inside tmux. Focus: a polished, discoverable UI that never freezes (OpenCode-style command palette and panels, btop-style colour and glyph graphics). It uses **presage** for the Signal protocol and never reimplements it. Licence: AGPL-3.0. Unofficial; not affiliated with Signal.

### Gotchas found so far

- **Web focus (D125):** DOM listeners only queue input; even a canvas `blur()` can run inside the shell's `borrow_mut`, so synchronous page focus handlers must never call a `Demo`/Rust API. Only an active canvas in a visible, focused document captures input. Resize and programmatic startup chat opening are not user input: never simulate keys to open the demo's first chat, or it claims focus and marks messages read. `Demo::inspect` shows `focused`/`open`; `shot.mjs` reports failed CDP evaluations in its logs (check them, not just the process exit code). Focus and Esc-to-leave are done; panel controls are next (4.3b). Owner checks: MANUAL_TESTS "Website: focus and Escape".

- `#[expect(...)]` on a macro call (`println!`) is ignored; put it on the enclosing `fn`.
- `#[tokio::test]` expands to `block_on`, which is banned: add `#[expect(clippy::disallowed_methods, reason = "#[tokio::test] expands to block_on; tests may block")]` (on the test fn, or once on the whole `mod tests`).
- Trait impls with `async fn` bodies that never `.await` trip `clippy::unused_async_trait_impl`. In real impls, write those methods as `fn ... -> impl Future<Output = ...>` returning `std::future::ready(...)` (see `mock.rs`).
- `wildcard_enum_match_arm` doesn't catch `_` inside tuple patterns; spell out variants by hand. In tests, prefer `let ... else` / `if let` over a `_ =>` arm.
- Blocking std calls (fs, `Path::exists`, sleep…) are banned everywhere; startup code and tests opt out per function/module with `#[expect(clippy::disallowed_methods, reason = "...")]`.
- `fastrand::Rng::choice` needs an `ExactSizeIterator`: collect a filtered iterator into a `Vec` first.
- Pedantic `too_many_lines` caps functions at 100 lines; split big `match`es into one method per arm.
- Commit and push automatically after each finished task or milestone (D33, superseding D23); don't wait to be asked.
- Store tests use real time, not `start_paused`: SQLite works on its own thread, so a paused clock auto-advances while waiting and timers fire early (D34).
- Pedantic clippy wants `as_chunks::<N>()` over `chunks_exact(N)`, `type` aliases at module level (`items_after_statements`), and `assert_eq!(v, vec![])` over `assert!(v.is_empty())`.
- Store SQL uses runtime `sqlx::query`/`query_as` with tuple rows (up to 16 columns), not `query!` (needs a DB at compile time).
- **Snapshots:** after a UI change run `INSTA_UPDATE=always cargo test -p faro-app`, then read `git diff crates/faro-app/src/ui/snapshots/` before committing (files are named `faro_app__ui__tests__*`). Snapshot files store cells, so wide or variation-selector emoji make rows look misaligned in the `.snap` file even when the layout is right.
- **Smoke-testing the TUI from an agent:** use a private tmux server and `respawn-pane` (chaining the command into `new-session` fails silently): `tmux -L faro-smoke -f /dev/null new-session -d -x 110 -y 30 -s s; tmux -L faro-smoke set -g remain-on-exit on; tmux -L faro-smoke respawn-pane -k -t s "./target/debug/faro --data-dir <scratch dir>"`. Drive it with `send-keys` (`M-Down`, `-l 'text'`, `C-q`), read it with `capture-pane -p`, then `kill-server`. Always use a scratch `--data-dir`.
- **Flood tests** need `faro demo --no-faults` as well as a small `--activity`, or the demo spends most of its time in scripted outages. Judge CPU on a release build; debug is several times slower and takes seconds to flush queued writes on quit.
- Key handling: match on `(code, modifiers)` tuples (no wildcard-lint trouble). Event handlers take `&Event` (`needless_pass_by_value`). `single_match_else` wants `if let ... else`.
- Pedantic `struct_excessive_bools` allows at most 3 `bool` fields per struct: group new flags into a small struct (as with `SidebarScroll`, `Selection`, `Environment`). Other lints met recently: `double_ended_iterator_last` (use `next_back()`), `manual_assert_eq` in tests, `single_match_else`.
- **Scripted multi-file edits:** `cargo fmt` reformats code after every run, so match against the formatted text and apply each file independently (a script that asserts on several files and stops at the first mismatch leaves the earlier files edited and the rest not).
- **Measure text after `sanitize`**, never before: in compatible emoji mode sanitising changes widths (D47). Anything drawn without sanitising (the input) is caught by `emoji::finish`, but a UI test fails if fixture text needs it.
- **inotify limit on the Debian machine:** the user is near `fs.inotify.max_user_instances` (256). The config watcher test then fails with "Too many open files" in a parallel `cargo test`, and faro shows "changes … won't apply until restart". This is environmental: confirm with `cargo test -p faro -- --test-threads=1`.
- **Never call `Terminal::clear()`** (or anything that reads the cursor position) once the event reader runs: the reply is swallowed and it fails after 2 s. Use `Tui::clear`.
- **Debugging terminal glitches (D47, D55):** `python3 tools/frames/record.py <scratch>/rec mixed --steps 250` (from the repo root, after `cargo build`) runs a scripted mock session in a private tmux, saving faro's raw output (`rec.bin`, via `pipe-pane`) and its intended frames (`frames.txt`, via `FARO_DEBUG_FRAMES`). `python3 tools/frames/replay.py <scratch>/rec [--nested] [--split N]` plays it back frame by frame (split on `\x1b[?2026l`) in a pane of the same size and compares `capture-pane` with the intended frame after each; `--nested` also checks an outer tmux attached to the replay (what a real client sees after tmux redraws). It prints the divergent-frame count and writes `replay-report*.txt`; `tools/frames/decode.py <dir> <frame> [row]` shows what one frame wrote after each cursor move. Read tmux's source (`screen-write.c` `screen_write_combine`, `utf8.c` `utf8_should_combine`) to explain a divergence. Scenarios: `mixed`, `type`, `switch`, `logo` (nothing open: idle spells, resizes through the logo forms, open/close a chat), `images` (half-block inline images, scrolling, overlays, image viewer popup); `--steady` skips resizes (nested replays with `--split` can't mirror them); a flood is `--activity 15`; `--split 40 --width 97` puts faro beside another pane. `--bubbles rounded|bar` pins the bubble style (the private tmux has no clients, so `auto` means bars there).
- **tmux joins what it receives onto the cell before the cursor**, even after a cursor move, comparing only that cell's first code point (D55): never draw a regional indicator right after a cell starting with one, or anything after a cell ending with a ZWJ; `emoji::finish` enforces this for the whole frame. Skin tones only join a fixed list of bases (`TMUX_SKIN_TONE_BASES`). And tmux 3.6 draws ☝ ⛹ ✌ ✍ 🏋 🏌 🕴 🕵 🖐 two cells wide even without VS16 (`TMUX_WIDE`). `capture-pane` can't show such width differences (it skips padding cells), so check widths with the replay or `#{cursor_x}`, not by eye.
- **Probing a glyph's width in tmux:** print it in a private tmux pane between two letters and read `#{cursor_x}` (`display -p`), also from an outer tmux attached to it for the nested view. In bash `printf`, `\U` takes up to 8 hex digits, so write `\U0001FB4A` (not `\U1FB4Ab`). Private-use glyphs (Powerline) may be dropped from captured text by your tools; check the bytes with `od -c`.
- **Run the quality gate with `set -o pipefail`** if you pipe its output (`cargo clippy ... | tail`): otherwise the pipe reports `tail`'s exit code and a failing gate looks green (this once let a lint failure get pushed).
- In the input context `Ctrl+K` is `DeleteToLineEnd` (pane bindings win over global ones), so keymap/rebinding tests use a free key like `F2`.
- `notify` reports `Access` events (e.g. our own reads); the watcher ignores them, or every reload would trigger another. Watch the parent directory, not the file: editors save by rename.
- `toml_edit` appends new tables/keys after the document's trailing comments; `config/edit.rs` inserts by text first and re-parses to check. Use `config::edit::set`, never raw `toml_edit` inserts, for writes.
- **Styles for selection and muted text come from the theme** (`theme.selected()`, `theme.muted()`, `theme.inverse(colour)`), never `bg(theme.background_element)` / `fg(theme.text_muted)` / `fg(theme.background)`: the `system` theme draws those with reverse video and dim instead of colours (D51). Patch muted onto a base with `base.patch(theme.muted())`.
- **A new faro theme** goes in `theme/builtin.rs`, `bundled::faro()` and the `theme` help text in `faro-core::config` (a test checks the help names every faro theme); the contrast tests in `theme/tests.rs` must pass unchanged, and RGB literals are written `Color::Rgb(0x.., 0x.., 0x..)` (clippy reads `0x10_12_16` as a mistyped suffix).
- The smoke-test tmux sets `TMUX`, so faro detects truecolor there; to see the 256-colour path, run it as `env -u TMUX COLORTERM= TERM=xterm-256color ./target/debug/faro …` and read colours with `capture-pane -p -e`.
- **Bundling another OpenCode theme:** drop the JSON in `crates/faro-app/themes/opencode/`, add it to `OPENCODE` in `theme/bundled.rs`, and bump the count in `theme/tests/files.rs`; imported themes aren't held to D51's rules, only to the D54 checks (`theme::tests::files`). OpenCode's resolver looks names up in `defs` before roles, and a role may name a def of its own name; keep `theme_file` doing the same.
- **The logo (D61) is drawn from `View::logo_time`, never the clock:** tests build `View { logo_time: None, .. }` for the still frame. A new animation should follow the same pattern (time in `View`, a `Geometry` flag saying a moving frame was drawn, a timer in the app loop that's off unless both say so) so idle faro never wakes up.
- **Fake terminals in tests must answer `ESC [ 5 n` with `ESC [ 0 n`:** with `inline_images = "auto"` and kitty clients, faro's startup image query (ratatui-image) waits 500 ms for it. If it never comes, ratatui-image's query thread stays blocked on stdin and eats the first keys typed (real terminals and tmux always answer it).
- **Smoke tests must pass `--config <scratch>/config.toml`** as well as `--data-dir`, or faro writes the template to the real `~/.config/faro`.
- **faro-app must build for the browser (D111):** no crossterm, ratatui-image, tokio, notify, std::fs or processes there. Platform work goes through an `Effect` the binary runs, or a trait the binary implements (`ImageCache`). Check with `cargo clippy -p faro-app --target wasm32-unknown-unknown -- -D warnings`.
- **`cargo build -p <crate>` resolves features for that crate alone**, not the workspace: something that only works because another crate turns a feature on (ratatui's `std` comes with the binary's crossterm feature) breaks there. Build faro-web and faro-app on their own when changing their dependencies.
- **clippy's test relaxations (`unwrap`, indexing, panics) need a plain `#[cfg(test)]`** on the module: `#[cfg(all(test, feature = "…"))]` hides it from clippy's test detection. Put the extra condition in a second `#[cfg]`.
- **A store change needs both engines:** `store/db.rs` (SQL) and `store/mem.rs` (memory) answer the same `Request`s and must agree; new store tests go through `engines!` in `store/tests.rs` unless they need a real file.

## Rules

1. **Follow PLAN.md in order** and update its Progress table when a milestone or notable task completes.
2. **Record decisions.** Any new or changed decision goes into DECISIONS.md (append; mark superseded entries) and DESIGN.md is updated to match. Mark agent-made calls as **Judgement**.
3. **Never block the UI thread.** No network or disk I/O in the reducer or render path (DECISIONS D22).
4. **No real Signal account before M7.** Use the mock backend. Before starting M7, ask the owner to prepare a **separate test account**. Never use the owner's main account for development.
5. **Never reimplement Signal protocol/service-layer code** (D4). Domain types are faro's own, not presage's (D6).
6. **Privacy:** never log message bodies or phone numbers by default; never commit Signal data, databases, keys or logs (see `.gitignore`).
7. **Quality gate before every commit:** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`.
8. **Git:** after finishing each well-defined chunk of work (a PLAN task or milestone), with the quality gate green, **commit and push without asking** (D33). Small commits, short imperative messages (e.g. "Add mock backend event generator"). Never rewrite pushed history.
9. **Prefer rules the tools enforce over conventions** (D27). When new code introduces a rule worth keeping (no panics, no blocking calls in the UI, no secrets in logs…), enforce it with lints, `clippy.toml` bans, CI checks or tests, and list it in PLAN.md "Ongoing: mechanical constraints".
10. **Terminal behaviour can't be fully verified by agents.** When a change affects rendering, input, mouse, colours or emoji, say so and add an item to [docs/MANUAL_TESTS.md](docs/MANUAL_TESTS.md) instead of claiming it works.

## Working with the owner

- Wants **plain, concise explanations** and clear recommendations with a default ("I'd do X; say if you prefer Y").
- Work, tests, commits and pushes happen in the development checkout (`/home/sergiu/work/faro`). **Never deploy the website or modify the owner's `/srv` instance**: the owner deploys manually. Say when a tested checkpoint is ready to deploy.
- Delegate implementation and review to the local Qwen agents to conserve the coordinator's quota. The owner monitors usage and will flag thresholds; prioritise small, committed and pushed checkpoints as a limit approaches.
- Wants to be **asked before big or irreversible decisions**; for smaller technical choices, use best judgement and record it.
- Values UI/UX polish highly; inspirations are **OpenCode** and **btop**.
- Runs faro inside **tmux**, often over **SSH**, in modern terminals like **kitty**; uses macOS (Mac mini host) and Linux (Arch, Debian).

## Delegating to the local subagents

The owner's Anthropic quota is limited; the `qwen` and `qwen-review` subagents run on a local model with no quota (owner's choice, 2026-10-12). Work this way:

- **`qwen` writes the code.** Give it a self-contained prompt: which docs/sections to read (AGENTS.md rules and gotchas always), the exact task and files, acceptance criteria, the commands to verify with (`set -o pipefail`), "don't commit", and "report in under N lines".
- **Keep tasks to one step.** Two empty runs on a large task (the SVG exporter) were fixed by splitting it: first a read-only analysis, then each edit as its own prompt in the same session. Follow-ups go to the same session (`sessionID`) so it keeps its context.
- **`qwen-review` reviews each chunk** (in the background while you write docs). Ask for HIGH/MEDIUM only, max ~8 findings. Its findings are usually right, but confirm the important ones in the code before acting; send the fixes back to the `qwen` session that wrote the code.
- **The main agent** plans the chunk, checks the results (diffs where small, renders with `rsvg-convert` or headless Chrome, reads screenshots), runs the full quality gate, writes DECISIONS/PLAN/AGENTS.md/MANUAL_TESTS, and commits and pushes. Read only the doc sections a chunk needs.
- Headless Chrome for screenshots: `~/.cache/ms-playwright/chromium_headless_shell-1228/*/chrome-headless-shell` (`--screenshot`, or `CHROME=` for `crates/faro-web/tools/shot.mjs`).
